# Аудит Windows-хостов: нагрузка, браузеры, история, закладки

Роль `windows_audit` и обёртка `collect_windows_audit.sh` собирают с
Windows-машин по WinRM снимок того, что происходит на хосте:

- систему и нагрузку: ОС, CPU, RAM, диски, uptime, IP, часовой пояс;
- все процессы: память, CPU, владелец, путь, командная строка;
- установленные и запущенные браузеры;
- историю посещений и закладки по профилям пользователей.

Результат — ZIP с «сырыми» данными на control-node и готовый HTML/CSV-отчёт.
Python на клиентах **не нужен**, всё собирает PowerShell 5.1.

## Зачем это и чем не является

Это инструмент **разового или регулярного аудита парка**, а не EDR и не
непрерывный мониторинг. Снимок делается в момент запуска: пока браузер
открыт, его база истории копируется «на лету» (через `FileShare.ReadWrite`),
останавливать браузер не нужно.

Похожие ручные `.bat`/Python-скрипты для одной машины остаются в `files/` и
в git не входят: для парка используйте роль — она не требует Python на
хосте, не зависит от `pause`, сама вывозит данные и строит сводный отчёт.

## Быстрый старт

```bash
cd ~/working/ansible_project

# посмотреть, какие хосты попадут в прогон
./collect_windows_audit.sh --limit 192.168.0.90 --list

# сначала один хост, история за 7 дней (по умолчанию)
./collect_windows_audit.sh --limit 192.168.0.90

# глубже по истории и без лишних вопросов для диапазона
./collect_windows_audit.sh --limit '192.168.0.14*' --history-days 30 --yes

# только нагрузка/процессы/браузеры, без персональных данных
./collect_windows_audit.sh --limit 192.168.0.90 --no-history --no-bookmarks

# проверить синтаксис, ничего не запуская
./collect_windows_audit.sh --syntax-check
```

Пароль WinRM спрашивается интерактивно (без эха) либо задаётся файлом:

```bash
./collect_windows_audit.sh --limit ... --password-file /run/secrets/winrm
ANSIBLE_WINRM_PASSWORD=... ./collect_windows_audit.sh --limit ...
```

В inventory и в git пароль не попадает.

## Что получается на выходе

```
reports/windows_audit/
  2026-11-23_101500/
    raw/
      ZR-90.zip              # сырые данные с хоста
    report/
      index.html             # сводка по хостам + фильтр
      hosts/ZR-90.html       # карточка хоста
      hosts/ZR-90.json       # те же данные для интеграций
      summary.csv            # одна строка на хост
      history.csv            # история посещений (все хосты)
      bookmarks.csv          # закладки (все хосты)
      top_processes.csv      # топ процессов по памяти
      REPORT_INFO.txt
  latest -> 2026-11-23_101500
```

`reports/` уже в `.gitignore`: отчёты содержат имена, URL и внутренние IP.

HTML открывается локально в браузере, внешних зависимостей нет. Сводка
фильтруется по хосту, ОС и браузеру; в карточке хоста — топ-20 процессов по
памяти и CPU, запущенные и установленные браузеры, история и закладки по
каждому профилю.

## Что именно собирается на хосте

Сборщик: `roles/windows_audit/files/Invoke-WindowsAudit.ps1` (формат 1.1).

| Файл в ZIP | Содержимое |
|---|---|
| `system.json` | ОС, сборка, CPU (ядра/потоки/загрузка), RAM, диски, IP, uptime, часовой пояс, текущий и консольный пользователь |
| `processes.csv` | все процессы: имя, PID/PPID, владелец, сессия, Working Set, private bytes, CPU-секунды, CPU %, время старта, путь, командная строка |
| `browsers.json` | установленные браузеры (имя, версия, exe) и запущенные процессы браузеров |
| `users/<user>/<browser>/<profile>/Bookmarks` | закладки Chromium-браузеров (JSON как есть) |
| `users/<user>/<browser>/<profile>/History` (+`-wal`, `-shm`, `-journal`) | история Chromium-браузеров (SQLite) |
| `users/<user>/Mozilla Firefox/<profile>/places.sqlite` (+`-wal`, `-shm`) | история и закладки Firefox |
| `meta.json` | пользователь, браузер, профиль, исходный путь, какие файлы скопированы |
| `warnings.txt` | что не удалось прочитать (нет прав, битая база, файл занят) |

Поддерживаются: Chrome, Edge, Yandex Browser, Brave, Vivaldi, Chromium,
Opera, Opera GX, Firefox. Профили ищутся по всем пользователям из
`ProfileList` (включая перенесённые каталоги вроде `D:\Users\ivan`), а не
только в `C:\Users`.

**Не собираются** `Cookies`, `Login Data`, `Web Data`, `Local State`,
`key4.db`, `logins.json` и другие файлы с паролями, токенами и сессиями.
Командные строки процессов могут содержать чувствительные аргументы —
поэтому отчёты и закрыты правами `0700/0600`, и не публикуются.

## Правовая часть (обязательно согласовать)

История посещений и закладки — это персональные данные сотрудников. Сбор
«просто потому что можем» незаконен. Перед боевым использованием:

1. **Локальный акт.** Пропишите в правилах внутреннего трудового распорядка
   или отдельном приказе: какие устройства/учётки подпадают под аудит, какие
   данные собираются, с какой целью, кто имеет доступ, сколько хранятся.
2. **Ознакомление.** Ознакомьте работников с актом под роспись (ТК РФ,
   ст. 86–88 — обработка персональных данных работников). Для некоторых
   случаев может понадобиться отдельное согласие.
3. **Минимизация.** Собирайте только то, что нужно для цели. Если задача —
   «понять, какие браузеры и какая нагрузка», запускайте с
   `--no-history --no-bookmarks`. Историю — только на срок, нужный для
   разбора, а не «за всё время».
4. **Только рабочие устройства и учётные записи.** Личные машины, личные
   профили браузера, чужие сессии — вне периметра.
5. **Доступ и хранение.** Каталоги отчётов — только у ответственного ИБ/ИТ,
   на диске с шифрованием, с резервным копированием, если это требуется.
   Права `0700` на каталоги и `0600` на файлы выставляются автоматически,
   но это не заменяет разграничение доступа на уровне сервера.
6. **Срок хранения и удаление.** Задайте срок (например, 30–90 дней) и
   удаляйте прогоны автоматически (см. ниже).
7. **Уведомления.** Если организация является оператором ПД, проверьте,
   нужно ли уведомление РКН и указаны ли такие обработки в политике.
8. **Инциденты.** Если данные используются для служебного расследования,
   фиксируйте цепочку: кто, когда и с каким `--limit` запускал сбор, где
   лежит архив, кто имел доступ.

Это не юридическая консультация: конкретные формулировки и необходимость
согласий согласуйте с юристом и ответственным за ПД.

## Регулярный запуск и хранение

Пример cron на control-node (раз в неделю, ночью, только рабочие хосты):

```cron
# WinRM-пароль — в файле с правами 600, не в crontab
0 2 * * 1 cd /home/zr_admin/working/ansible_project && \
  ./collect_windows_audit.sh --limit '192.168.0.*' --history-days 7 \
  --password-file /home/zr_admin/.secrets/winrm --yes >> reports/cron.log 2>&1
```

Удаление старых прогонов (оставляем 8 недель):

```bash
find ~/working/ansible_project/reports/windows_audit \
  -mindepth 1 -maxdepth 1 -type d -mtime +56 -exec rm -rf {} +
```

Учтите, что `latest` — символическая ссылка; `find -type d` её не тронет.

## Переменные роли

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `wa_report_dir` | `reports/windows_audit` | куда роль складывает ZIP в `raw/` (обёртка подставляет каталог прогона) |
| `wa_include_history` | `true` | копировать базы истории |
| `wa_include_bookmarks` | `true` | копировать закладки |
| `wa_include_profiles` | `true` | обходить профили пользователей |
| `wa_collect_timeout` | `1200` | сколько секунд ждать сборщик (`async`/`poll`) |
| `wa_keep_remote_zip` | `false` | оставить ZIP на хосте |
| `wa_keep_remote_script` | `false` | оставить `.ps1` на хосте |

Прямой запуск плейбука (без обёртки):

```bash
ansible-playbook -i inventory/windows_hosts.yml playbooks/windows_audit.yml \
  --limit 192.168.0.90 --connection-password-file /path/to/pass \
  -e wa_report_dir=/tmp/audit
```

## Разбор без сбора

Отчёт можно пересобрать из уже собранных ZIP с другой глубиной истории:

```bash
python3 scripts/parse_windows_audit.py \
  --raw reports/windows_audit/latest/raw \
  --out /tmp/audit-report \
  --history-days 0          # 0 = вся история в базах
```

Полезные ключи: `--max-history N` и `--max-bookmarks N` (сколько строк
показывать в HTML; CSV всегда полные), `--title`, `--top`.

## Ограничения и что делать, если пусто

- **Нет прав администратора** — роль падает на первом шаге с понятным
  сообщением. Учётка WinRM должна быть локальным админом.
- **История пустая, закладки есть** — браузер мог держать базу эксклюзивно
  или база битая; смотрите `warnings.txt` и `REPORT_INFO.txt`. Обычно
  помогает повторный сбор: `-wal`/`-shm` копируются вместе с базой.
- **Профиль не найден** — профиль мог быть создан после сбора, лежать на
  отключённом диске или быть гостевым (`Guest Profile`/`System Profile`
  пропускаются намеренно).
- **Firefox** хранит историю в `%APPDATA%`, а не в `%LOCALAPPDATA%` — это
  учтено. Контейнеры Firefox (`containers.json`) не разбираются: история
  общая на профиль. Firefox из Microsoft Store (пакет `Mozilla.Firefox`)
  хранит профиль в `%LOCALAPPDATA%\Packages\...` и пока не сканируется —
  для него используйте классический MSI.
- **Время** в отчёте пересчитывается в часовой пояс хоста на момент сбора.
  При переходах на летнее/зимнее время старые записи могут смещаться на час.
- **Пусто в `history.csv`** — проверьте `--history-days`: по умолчанию 7
  дней от момента сбора. Для всей истории базы используйте `0`.
- **Хост недоступен** — Ansible вернёт код 4, обёртка это переживёт и
  разберёт архивы с остальных хостов.

## Почему не «просто прочитать базу по сети»

Chrome/Edge/Firefox держат SQLite открытым и пишут в WAL. Копирование
файла по SMB «как есть» часто даёт `database is locked` или потерянные
последние записи. Сборщик открывает файл с `FileShare.ReadWrite|Delete`,
копирует основной файл и WAL/SHM/Journal рядом, а разбор уже идёт на
control-node по локальной копии.
